# 开发 harness

这里的 harness 是让代理能够定位代码、实施修改、获取测试反馈并交付证据的工作环境。本仓库不需要额外接入模型 API 才能开发。

## 现状与文档分工

截至 2026-10-03，确定性测试、竞态检查、容器冒烟和限资源压测已经存在；本次补齐根目录代理入口，并把验证选择与历史结果分开。

| 入口 | 职责 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 自动加载的短指引：代码地图、兼容约束、验证入口 |
| [README](../README.md) | 应用定位、用户功能与环境变量 |
| [testing.md](testing.md) | 按改动选择验证、可复现命令、覆盖边界 |
| [deployment.md](deployment.md) | Docker / Heroku 发布与线上验收 |
| [native-webp-testing.md](native-webp-testing.md) | 有日期和条件的性能实验记录 |
| [test.yml](../.github/workflows/test.yml) | CI 实际执行的检查 |

行为以代码和可复现测试为依据；文档不一致时同步修正文档。保留一份根 `AGENTS.md`，暂不增加目录级指引、重复的 `CLAUDE.md`、空计划模板或模型专用规则副本。

## 面向 GPT-6 Astra 的用法

以下模型事实来自 [官方模型页](https://developers.openai.com/api/docs/models/gpt-6-astra)，于 2026-10-03 核对；右侧是本项目的实践建议，不是模型性能保证。

| 官方能力 | 本项目采用方式 |
| --- | --- |
| 复杂推理与编码；可调整 reasoning effort | 普通修复先用 `medium`；涉及并发、取消、资源生命周期或跨层兼容时再考虑 `high`。不固定使用 `max` |
| 长上下文 | 跨层问题可同时读取 gateway、图片预算和回归测试；仍按需加载，历史日志与整个 provider 集合不必预先塞入上下文 |
| 函数调用与工具支持 | 用文件读取、diff、编译、HTTP 和测试结果验证判断；模型可支持某工具不代表当前客户端已提供该工具 |
| 图像输入 | 修改 `/docs` 界面时可检查截图；后端接口仍通过状态码、响应结构和测试验证 |

在 Codex 客户端可用的模型列表中选择 GPT-6 Astra；可用的推理档位以客户端为准。`AGENTS.md` 不会切换模型。本仓库不强制用户级配置，也不修改服务中遗留的翻译模型设置。上述流程同样适用于其他编码模型。

Codex 的指引发现机制见 [官方 AGENTS.md 文档](https://developers.openai.com/codex/guides/agents-md)。从本仓库打开任务，让项目级指引与当前客户端指令一起生效。

## 一次任务如何闭环

1. 确认目标、验收条件、已有修改和相关入口。简单修改直接实施；跨层问题先列出短计划和待验证假设。
2. 做最小完整修改，保留兼容约束。仅并行读取互不依赖的信息；编辑同一文件、迁移和发布按依赖顺序执行。
3. 用 [测试矩阵](testing.md#按变更选择验证) 检查受影响行为。失败时区分实现缺陷、依赖/工具链问题、外站不可用，不通过跳过断言制造成功结果。
4. 根据证据修正，再交付 diff、验证结果及剩余边界。新增 API/配置/部署行为同步更新其唯一文档入口。

任务要求尽量描述结果，例如：“修复客户端断开后像素额度提前释放的问题；保持其他等待者可继续取得结果；用本地图片夹具验证取消和资源上限。”具体实现由代码与证据决定。

长任务续接时只保留：目标与约束、修改文件/提交、已执行命令及结果、未解决问题、下一步。可以放在聊天摘要或 PR 中；确实需要跨会话保存在仓库时再创建任务记录，不默认维护永远增长的状态文件。部署记录应包含应用名、发布提交、验证结果；不保存密钥，旧运行状态不能当作实时状态。

## 仍然存在的验证缺口

- `make verify` 小于完整 CI；CI 当前只构建默认 Dockerfile，没有自动构建 `Dockerfile.heroku`。Heroku 兼容性仍需部署构建与 HTTP 验收。
- 没有自动化的真实 Jellyfin/Emby 客户端验收；外站抓取测试与确定性服务测试分开执行。
- 历史覆盖率未设为 CI 阈值，性能数据也不是持续基准或吞吐保证。

遇到重复失败再补相应的自动检查；目前优先复用现有命令和测试夹具，不为了文档完整而引入新框架。
