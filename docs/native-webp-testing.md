# 原生 WebP 与分辨率并发控制实测

测试日期：2026-10-03。测试应用：`metatube-webp-lab-c4349d`，Heroku 美国区、Eco 类型。原有 `metatube-app-us` 未修改。

## 实现

Docker 使用动态链接的 Go 二进制及原生 `libwebp`、`libwebpdemux`。启动时检查后端，日志必须显示 `WebP backend: native libwebp`；生产镜像设置 `REQUIRE_NATIVE_WEBP=1`，加载失败会停止启动。输出仍为有损 WebP，质量固定 80。

仅安装动态库并不能让原来的静态 Go 二进制使用原生后端，因此构建也改为动态链接。普通本地构建仍支持纯 Go 回退。

图片缓存未命中时，先合并相同请求，再进入有界队列。最多 4 个 SDK 请求进入处理阶段，额外等待最多 16 个不同图片任务。读取受限的压缩数据并检查真实分辨率后，在完整解码之前申请像素额度；额度一直持有到裁剪、水印和编码结束。

默认 `IMAGE_PIXEL_BUDGET=6000000`：

- 1200×1800（216 万像素）：最多两张同时进入解码/编码。
- 2000×3000（600 万像素）：独占额度。
- 超过 600 万、未超过 2000 万像素：独占额度，等待其他图片结束。
- 大图排队时后来的小图不能不断插队；取消的等待者会退出。

等待时间包含在默认 25 秒请求时限内。队列满返回 503，等待超时返回 504。相同图片共用任务，一位客户端断开不会取消其他客户端仍在等待的结果；所有客户端离开后取消任务。已经进入原生编码的任务不能强制中断，直到实际结束才释放额度，防止超时后不断启动新的编码任务。

`GOMEMLIMIT=192MiB` 是 Go 的软目标，不包含原生库内存，不是 192 MiB 的进程上限。像素额度是并发控制，不是精确的内存计量。压缩输入仍有单张 16 MiB 上限；等待解码的已下载数据也占内存，因此不应在 Eco 上随意提高 `MAX_CONCURRENT`。

## 本地限资源对比

同一批合成 JPEG，解码、裁剪、WebP 80 编码，1 CPU、512 MiB 硬限制且禁止额外 swap。旧镜像使用纯 Go 后端，新镜像使用原生后端及上述 Go 内存软目标。

| 场景 | 旧镜像 | 原生镜像（此表尚未启用像素排队） |
| --- | --- | --- |
| 1200×1800，逐张，8 次 | 平均 1.36 秒，峰值 134 MiB | 平均 0.33 秒，峰值 55 MiB |
| 2000×3000，逐张，4 次 | 平均 3.66 秒，峰值 363 MiB | 平均 0.93 秒，峰值 151 MiB |
| 2000×3000，4 路并发 | 内存不足终止 | 完成，峰值 408 MiB |
| 4000×5000，单张 | 内存不足终止 | 完成，峰值 322 MiB |

启用像素队列后的完整 HTTP 服务测试包含元数据查询、图片下载、编码、缓存、测试图片服务和混合压力。整个容器观测峰值为 **399.7 MiB**，没有 OOM。峰值包含测试夹具的开销，不能与上表的单独处理程序直接等同。

## Heroku Eco 实际测试

在独立 Eco one-off dyno 中运行处理程序，原生后端检查通过，进程正常退出。216 万像素图片平均约 0.36 秒/张，600 万像素约 0.99 秒/张。4 个 600 万像素任务经队列处理约 4.01 秒，进程峰值 RSS 约 161 MiB；4 个 2000 万像素任务约 11.58 秒，峰值 RSS 约 364 MiB。这些 RSS 数值只属于处理程序，不是完整 web dyno 的内存峰值。

独立 Eco web dyno 的实际 HTTPS 请求结果如下：

| 同时到达的请求 | 总耗时 | 结果 |
| --- | ---: | --- |
| 4 张 216 万像素 JPEG | 1.41 秒 | 4 个 200 |
| 4 张 600 万像素 JPEG | 5.26 秒 | 4 个 200 |
| 4 张 2000 万像素 JPEG | 13.06 秒 | 4 个 200 |
| 2 张文件较小、但有 2000 万像素的 PNG | 3.26 秒 | 2 个 200 |
| 12 个大、中、小图片混合请求 | 17.05 秒 | 12 个 200 |
| 32 张 2000 万像素图片 | 25.61 秒 | 8 个 200、12 个 503、12 个 504；服务仍就绪 |

响应检查包含 `image/webp`、RIFF/WEBP 文件头。生产镜像的独立冒烟测试还验证了认证、ETag/304、HEAD、相同图片不同旧 quality 参数共用缓存，以及容器重建后 SQLite 数据保留。

测试图片由本地 HTTP 夹具提供，未测试真实第三方站点、Jellyfin/Emby 客户端，也没有实际处理完整 1 万张。Eco CPU 是共享资源，这些结果不是吞吐保证；1 万张批量刷新仍需客户端控制并发并重试 503/504。

## 复现

```sh
# 原生后端和竞态测试（原生后端不可用会失败）
docker build --target test -t metatube:native-tests .

# 生产镜像不含测试夹具
docker build -t metatube:production .
python3 scripts/smoke.py metatube:production

# 独立测试镜像；只部署到测试应用
docker build --target loadtest -t metatube:loadtest .
docker run -d --name metatube-loadtest --memory=512m --memory-swap=512m --cpus=1 -p 127.0.0.1:18080:8080 metatube:loadtest
python3 scripts/loadtest.py http://127.0.0.1:18080
docker rm -f metatube-loadtest

# 原生处理程序；-budget 0 可关闭额度用于对比
docker run --rm --memory=512m --memory-swap=512m --cpus=1 --entrypoint /usr/local/bin/eco-bench metatube:loadtest -w 2000 -h 3000 -c 4 -n 4 -budget 6000000
```

最终测试应用保留，测试结束后将 web 数量缩为 0；一次性测试 dyno 均已结束，避免继续占用 Eco 时长。
